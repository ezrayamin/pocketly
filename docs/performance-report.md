# Performance Report: bare RN vs RN + KMP

> **Status: interim (M1).** Only BM-01 (startup) and BM-08 (size) have been measured, on one
> mid-range device. Numbers come from `benchmarks/results/**/summary.md`, generated by
> `benchmarks/scripts/collect.ts`; none are typed by hand except where a table quotes them.
> Template: [benchmarking.md](benchmarking.md) §8.

## TL;DR (so far)
- **Users download +264 KB (+3.9%) more with KMP** on arm64 (Play download size). The APK
  difference is larger (+835 KB) only because APKs store native libraries uncompressed.
- **The size cost looks fixed, not proportional:** +822 KB → +835 KB APK while the app grew by
  ~1.7 MB. Almost all of it is the Nitro-generated bridge library, not the Kotlin core.
- **Startup is the same in both builds.** On the real Home screen, KMP's time to fully drawn is
  +3 ms (95% CI −7 to +14 ms). Startup is dominated by React Native rendering; Kotlin's own
  threads use ~2 ms of CPU.
- **So KMP's chance to win is in CPU-heavy work (BM-03, BM-04) and streams (BM-05), not startup.**

## Setup
- Device: vivo V2538 · Snapdragon SM7750 · 8 GB · Android 16 (mid-range tier). No low-end device yet.
- App: React Native 0.87.1 (New Architecture, Hermes) · Kotlin 2.2.0 · Nitro Modules 0.37.1 ·
  release builds, R8 on.
- Sessions:

## Hypotheses vs results
| ID | Hypothesis | Result | Confirmed? |
|---|---|---|---|
| H1 | CPU-heavy work is faster in Kotlin | not measured yet (BM-03, BM-04) | — |
| H2 | JS-thread CPU is lower during streams in `kmpCore` | not measured yet (BM-05) | — |
| H3 | Many tiny calls are slower in `kmpCore` | not measured yet (BM-06) | — |
| H4 | Scrolling and animation are the same (control) | not measured yet (BM-02, BM-07) | — |
| H5 | `kmpCore` is slightly larger | +264 KB download (+3.9%), +835 KB APK (+4.7%), arm64 | **Confirmed (interim)** |
| H6 | Cold start differs by < 10% | TTFD +3 ms (95% CI −7 to +14 ms), i.e. < 3% | **Confirmed (interim)** |
| H7 | A Baseline Profile helps `kmpCore` more | not measured yet (BM-09) | — |

**Note under H6.** One Perfetto trace per build shows where startup time goes: after the first
frame, the UI thread spends ~170 ms mounting and drawing Home's native views, and the JS thread
~145 ms on the bundle and React render. Per-thread CPU is nearly identical between builds, and
Kotlin's own threads use ~2 ms. Where the business logic runs barely matters at startup, so the
cases where KMP could win are BM-03, BM-04 and BM-05.

## Results by scenario

### BM-01: cold start → Home rendered
Session `2026-10-04_mid-01`, 2 warm-up + 20 measured per build, alternating, all launches cold.

| Metric | jsCore median | kmpCore median | Shift (kmp − js) | 95% CI | p |
|---|---:|---:|---:|---|---:|
| Time to initial display | 252.0 ms | 251.5 ms | +1.0 ms | −6.0 to +9.0 ms | 0.80 |
| Time to fully drawn (Home with data) | 473.5 ms | 481.0 ms | +3.0 ms | −7.0 to +14.0 ms | 0.69 |

Shift is the Hodges–Lehmann estimate; the CI is distribution-free and states the largest
difference this setup can rule out. CV ≤ 4.9% in every row.

**Across sessions** (not a build comparison): time to fully drawn rose from ~294 ms (placeholder)
to ~474–481 ms (real Home) in **both** builds. That's the cost of a real screen. Compare builds
within a session only.

### BM-08: app size (arm64-v8a)

| | jsCore | kmpCore | Δ |
|---|---:|---:|---:|
| **Download size** (bundletool `get-size total`, max) | 6,820 KB | 7,084 KB | **+264 KB (+3.9%)** |
| APK file (split per ABI) | 17,774 KB | 18,609 KB | +835 KB (+4.7%) |

Every ABI shows a +3.6–3.9% download delta. **Why the two differ:** native libraries are stored
uncompressed in the APK (so they can be mapped directly), and Play compresses the download.
The APK delta is mostly native code, so it shrinks most in the download.

**What adds the bytes** (APK, arm64):

| Part | Δ kmpCore − jsCore |
|---|---:|
| Native libs (`libPocketlyCoreKmp.so`: Nitro-generated C++ bridge) | +763 KB |
| Dex (Kotlin core + coroutines, serialization, Koin, after R8) | +85 KB |
| JS bundle (no `core-js` in kmpCore) | −13 KB |

**Is the cost fixed or growing?** Track it every session:

| Session | jsCore APK | Δ APK | Δ download |
|---|---:|---:|---:|
| skeleton (`2026-10-03`) | 16,025 KB | +822 KB | not measured |
| Home (`2026-10-04`) | 17,774 KB (+1,749 KB) | +835 KB | +264 KB |

Flat so far, while the app grew by 1.7 MB. If the delta grows with each contract method
(the bridge library is generated per method and struct), that's a finding too.

## Limitations
- One mid-range device; no low-end device yet. Android only.
- In-process fake backend; in-memory storage until SQLite lands (ADR-0004 §7).
- BM-01 uses platform startup logs instead of Macrobenchmark, which is unreliable on this ROM
  (benchmarking.md §5); page cache isn't dropped between runs (no root), the same for both builds.
- `libNitroModules.so` (958 KB APK) ships in **both** builds (ADR-0003), so the deltas above
  understate the total cost of adopting Nitro + KMP from a bare app.
- Trace findings come from one cold start per build: indicative, not statistics.

## Not part of the comparison
The ~170 ms of UI-thread work after the first frame (mounting SVG icons, the gradient, the
list) is paid equally by both builds. Lighter icons or fewer views would make **both** faster,
which is a UX improvement, not a KMP finding. Deferred.

## When I'd choose each
_After BM-03 to BM-06. So far: neither startup nor download size is a reason to avoid KMP._
