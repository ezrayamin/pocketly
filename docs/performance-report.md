# Performance Report: bare RN vs RN + KMP

> **Status: interim (M2).** BM-01 (startup), BM-08 (size) and BM-02 (scrolling, the control)
> have been measured, on one mid-range device. Numbers come from `benchmarks/results/**/summary.md`, generated by
> `benchmarks/scripts/collect.ts`; none are typed by hand except where a table quotes them.
> Template: [benchmarking.md](benchmarking.md) §8.
>
> **Current code:** BM-01 and BM-08 were rerun on the slice-4 code (`2026-10-05_mid-02`: SQLite
> storage, local replica, History). Earlier sessions stay below as history.

## TL;DR (so far)
- **kmpCore is now 423 KB (4.7%) smaller to download on arm64, but only because jsCore bundles
  SQLite.** Storage differs by design (ADR-0009): op-sqlite ships its own SQLite build in
  jsCore (1,564 KB in the APK), while kmpCore uses the phone's. **The KMP architecture itself
  still costs about +250 KB of download (+918 KB APK)**, mostly the Nitro-generated bridge
  library. KMP doesn't make apps smaller; choosing the platform's SQLite does.
- **The architecture's cost is roughly fixed:** +822 KB → +835 KB → +918 KB APK across three
  sessions while the app grew by 7 MB.
- **Startup is the same in both builds** (within the 5% rule). With slice 4's storage, kmpCore
  now reaches "fully drawn" 17 ms *sooner* (95% CI −26 to −8 ms, −3.1%): Home's first load
  syncs and reads SQLite, which kmpCore does in Kotlin off the JS thread. Small, but the first
  measurable KMP advantage on real work.
- **Scrolling is the same in both builds (BM-02, the control).** Flinging through 1,000 History
  entries: frame rate +0.1%, app CPU −3.7%, JS-thread CPU −2.7%, peak RAM +0.5%, none of
  them meaningful. The setup is fair, so differences found in other scenarios can be trusted.
- **So KMP's chance to win is in CPU-heavy work (BM-03, BM-04) and streams (BM-05), not startup.**

| H6 | Cold start differs by < 10% | Slice 4: TTID +4 ms (CI −3 to +11), TTFD −17 ms (CI −26 to −8 ms, −3.1%, kmpCore faster). Home slice: TTFD +3 ms | **Confirmed (interim)** |
| H7 | A Baseline Profile helps `kmpCore` more | not measured yet (BM-09) | — |

**Note under H6.** One Perfetto trace per build shows where startup time goes: after the first
frame, the UI thread spends ~170 ms mounting and drawing Home's native views, and the JS thread
~145 ms on the bundle and React render. Per-thread CPU is nearly identical between builds, and
Kotlin's own threads use ~2 ms. Where the business logic runs barely matters at startup, so the
cases where KMP could win are BM-03, BM-04 and BM-05.

## Results by scenario

### BM-01: cold start → Home rendered
Session `2026-10-05_mid-02` (slice 4), release builds, 2 warm-up + 20 measured per build,
alternating, all launches cold. Battery 32.2–33.0 °C.

| Metric | jsCore median | kmpCore median | Shift (kmp − js) | 95% CI | p |
|---|---:|---:|---:|---|---:|
| Time to initial display | 256.5 ms | 260.5 ms | +4.0 ms | −3.0 to +11.0 ms | 0.19 |
| Time to fully drawn (Home with data) | 527.5 ms | 511.0 ms | **−17.0 ms** | −26.0 to −8.0 ms | 0.001 |

Shift is the Hodges–Lehmann estimate; the CI is distribution-free and states the largest
difference this setup can rule out. CV ≤ 4.3% in every row.

**Time to fully drawn.** The shift is real (p = 0.001, IQRs don't overlap) but below the 5%
threshold, so by the §4.3 rule it is not a meaningful difference. Its direction fits slice 4:
before Home can draw, it now syncs the server's changes into the replica and reads wallet, recent
transactions and the monthly summary from SQLite. kmpCore does that in Kotlin on its own
threads; jsCore does it in JS on the JS thread (plus op-sqlite's native calls).

Earlier session (`2026-10-04_mid-01`, Home slice, in-memory storage): TTID +1.0 ms (CI −6 to
+9), TTFD +3.0 ms (CI −7 to +14).

**Across sessions** (not a build comparison): time to fully drawn went from ~294 ms
(placeholder) to ~474–481 ms (real Home) to ~511–528 ms (slice 4: replica sync and SQLite reads,
navigation) in **both** builds. Compare builds within a session only.

### BM-02: scroll History, 1,000 entries (control)
Session `2026-10-05_mid-01`, `perf` builds, 1 warm-up + 10 measured iterations per build in 5
alternating blocks of 2. Each iteration: cold start on History with 1,000 entries (not
measured), then 3 passes of 96 flings top → bottom (measured). Each block started at ≤ 40 °C;
average block start 38.2 °C (jsCore) vs 38.1 °C (kmpCore).

| Metric (mean per iteration) | jsCore median | kmpCore median | Shift (kmp − js) | 95% CI | p |
|---|---:|---:|---:|---|---:|
| Frame rate | 44.5 fps | 44.6 fps | +0.1 fps | −0.3 to +0.5 fps | 0.68 |
| CPU, whole app (100% = 1 core) | 127.2% | 122.5% | −3.7% | −9.4 to +1.7% | 0.35 |
| CPU, JS thread (`mqt_v_js`) | 55.2% | 53.7% | −0.6% | −3.6 to +0.7% | 0.39 |
| CPU, UI thread | 26.6% | 26.6% | −0.0% | −0.6 to +0.4% | 0.97 |
| CPU, RenderThread | 30.7% | 28.9% | −1.4% | −5.8 to +0.8% | 0.16 |
| Peak RAM | 347.0 MB | 348.6 MB | −5.4 MB | −25.2 to +13.0 MB | 0.57 |

No metric passes the §4.3 rule (> 5% **and** non-overlapping IQRs). CV is ≤ 7.8% for every row
except RenderThread CPU (17–20%): three iterations (two jsCore, one kmpCore, each the second of
its block) ran at 40–47% RenderThread CPU and ~42.3 fps, against 26–36% and ~44.5 fps for the
rest. It affects both builds alike; the primary metrics (frame rate, JS and UI thread) have
CV ≤ 4.7%.

**Reading the frame rate.** The display ran at 60 Hz, and every half-second sample in both
builds lies between 38 and 60 fps with the same distribution (p10 38.3, p50 42.4 vs 42.5, p90
54.1 vs 54.2). The average is below 60 because each injected fling is a separate `adb` call:
the list coasts to rest between flings, and Android draws nothing when nothing moves. So it
reflects the gesture rhythm, not jank, and it is identical in both builds, which is what a
control should show.

**Why the control holds.** Scrolling reads the local replica 20 rows at a time and renders
them; the work is FlashList layout and native drawing, which is the same code in both builds.
The core is only called once per page.

### BM-08: app size (arm64-v8a)
Session `2026-10-05_mid-02` (slice 4: SQLite storage, History). Release builds, split per ABI.

| | jsCore | kmpCore | Δ |
|---|---:|---:|---:|
| **Download size** (bundletool `get-size total`, max) | 8,914 KB | 8,491 KB | **−423 KB (−4.7%)** |
| APK file (split per ABI) | 23,319 KB | 22,673 KB | −645 KB (−2.8%) |

Every ABI's APK is smaller in kmpCore (−405 to −805 KB). **That total mixes two effects**, which
the per-library breakdown separates:

| Effect (kmpCore − jsCore) | APK, measured | Download, estimated¹ |
|---|---:|---:|
| **Storage choice:** `libop-sqlite.so`, op-sqlite's bundled SQLite, in jsCore only | −1,564 KB | ≈ −719 KB |
| **KMP architecture:** everything else | **+918 KB** | **≈ +250 KB** |
| · `libPocketlyCoreKmp.so` (Nitro-generated C++ bridge) | +864 KB | ≈ +208 KB |
| · Dex (Kotlin core, SQLDelight, coroutines, serialization, Koin, after R8) | +118 KB | +118 KB |
| · JS bundle (no `core-js` in kmpCore) | −74 KB | −74 KB |
| Total | −645 KB | −423 KB measured |

¹ bundletool reports download size per build, not per file. Each native library's share is
estimated by compressing it (`gzip -9`); dex and the JS bundle are already compressed in the
APK. The estimates add up to −467 KB against −423 KB measured, so read them as ±50 KB.

**What this means.** The comparison is realistic: most React Native apps that need SQLite ship a
bundled one, as op-sqlite does. But the size win comes from that storage choice, not from KMP.
An app that already bundles SQLite would see roughly the architecture's cost, about +250 KB of
download; one that could use the platform's SQLite from JavaScript too would lose the win.

**Is the architecture's cost fixed or growing?** Tracked every session (APK, arm64):

| Session | jsCore APK | Δ APK, architecture | Δ APK, total | Δ download, total |
|---|---:|---:|---:|---:|
| skeleton (`2026-10-03`) | 16,025 KB | +822 KB | +822 KB | not measured |
| Home (`2026-10-04`) | 17,774 KB | +835 KB | +835 KB | +264 KB |
| slice 4 (`2026-10-05_mid-02`) | 23,319 KB | +918 KB | −645 KB | −423 KB |

Roughly fixed while the app grew by 7 MB (navigation, FlashList, op-sqlite). The bridge library
grew by 101 KB with slice 4's new bridged types and methods (StaleInfo, DatasetSeed,
`lastStorageMs`), consistent with it being generated per method and struct.

## Limitations
- One mid-range device; no low-end device yet. Android only.
- In-process fake backend, persisted in SQLite like the replica (ADR-0009). Numbers measured before slice 4 used in-memory storage and are not comparable with later runs.
- BM-01 uses platform startup logs instead of Macrobenchmark, which is unreliable on this ROM
  (benchmarking.md §5); page cache isn't dropped between runs (no root), the same for both builds.
- `libNitroModules.so` (958 KB APK) ships in **both** builds (ADR-0003), so the deltas above
  understate the total cost of adopting Nitro + KMP from a bare app.
- Trace findings come from one cold start per build: indicative, not statistics.
- BM-02 drives the flings with `adb shell input` rather than Maestro, whose driver hangs on this
  ROM (benchmarking.md §5). Fling cadence is set by `adb` (~0.25 s per fling), the same for both
  builds. Flashlight's frame-time tracer dropped events in 2 of the 20 iterations (234 and
  14,738 lost events); their frame rates sit inside the rest of the distribution, so they stay in.
- BM-02 ran over USB with the phone on its charger; a first attempt over wireless `adb` lost its
  connection, and an earlier attempt without a temperature gate drifted from 39 °C to 45 °C and
  was discarded.

## Found by benchmarking
BM-02 crashed `jsCore` mid-scroll on its first attempt: *"Unable to find parentView for tag"*,
preceded by dozens of *"Unable to find viewState for tag"* warnings per run, on the phone and
(fewer) on an emulator. Cause: React Native 0.87 keeps its native view registry in an
`androidx.collection` map that versions 1.4.0–1.4.2 can corrupt
([reactwg/react-native-releases#1426](https://github.com/reactwg/react-native-releases/issues/1426)),
and the app resolved 1.4.2. Fast list recycling loses views until a missing parent crashes the
app. Forcing `androidx.collection` 1.4.4 (`apps/mobile/android/app/build.gradle`, until RN 0.88)
took the warnings from 24–73 per run to 0 in both builds. Both builds had the bug; it would
have hit users of either.

## Not part of the comparison
The ~170 ms of UI-thread work after the first frame (mounting SVG icons, the gradient, the
list) is paid equally by both builds. Lighter icons or fewer views would make **both** faster,
which is a UX improvement, not a KMP finding. Deferred.

## When I'd choose each
_After BM-03 to BM-06. So far: neither startup nor download size is a reason to avoid KMP._
