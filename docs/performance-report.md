## TL;DR (so far)
- **KMP pays off when the work happens where the data already is, and only results cross the
  bridge.** Spending summary over 10,000 entries (BM-03): the entries stay on the native side and
  a ~2 KB summary crosses; 42 vs 53 ms end-to-end (−20%), the calculation itself 0.4 vs 4.7 ms.
  Ingesting 5,000 transactions (BM-04): 1.3 MB of JSON must cross into Kotlin first, which costs
  ~10 ms; kmpCore is **10–25% slower** (71 vs 65 ms, and 81 vs 65 ms in a second session).
- **If the core owns the network, the bridge cost disappears (BM-04b), but KMP doesn't win
  either.** With the payload already in the core, kmpCore's bridge overhead drops from 9.9 to
  0.7 ms and the import is 73 vs 66 ms, no meaningful difference. Kotlin parses faster for the
  first ~10 imports in a process (~60 ms end-to-end), then slows down for the rest of the launch
  (~76 ms), probably garbage collection; not investigated yet.
- **The earlier "KMP writes twice as fast" was jsCore's code.** Once jsCore writes the way
  kmpCore does (one prepared statement in one transaction), writing takes the same 39–40 ms in
  both. The fair comparison only appeared once both cores used the same write strategy.
- **Both processes start the same size; kmpCore keeps more after heavy work.** At launch they are
  within ~5 MB (PSS ~116 MB at Home). After repeatedly parsing 1.3 MB payloads, kmpCore holds
  ~60 MB more during the benchmark and ~110 MB more a minute later (clean pages in the ART heap;
  live objects are the same 5 MB). jsCore returns to its launch size.
- **A bridge call costs ~0.3 µs; data costs more.** A call that does nothing takes ~0.42 µs
  through Nitro vs ~0.12 µs in plain JS, so trivial calls really are ~3.5× slower in kmpCore.
  Formatting money costs ~1.1 µs in JS and ~0.22 µs in Kotlin, so moving it still wins (10,000
  calls: 10.6 vs 13.3 ms). Rule: moving a function to Kotlin pays off when it saves more than
  ~0.3 µs per call. Moving data is the real cost: 9.8 ms for a 1.3 MB string, 0.6 ms for a
  summary.
- **kmpCore is now 423 KB (4.7%) smaller to download on arm64, but only because jsCore bundles
  SQLite.** Storage differs by design (ADR-0009): op-sqlite ships its own SQLite build in
  jsCore (1,564 KB in the APK), while kmpCore uses the phone's. **The KMP architecture itself
  still costs about +250 KB of download (+918 KB APK)**, mostly the Nitro-generated bridge
  library. KMP doesn't make apps smaller; choosing the platform's SQLite does.
- **The architecture's cost is roughly fixed:** +822 KB → +835 KB → +918 KB APK across three
  sessions while the app grew by 7 MB.
- **Startup is the same in both builds** (within the 5% rule). With slice 4's storage, kmpCore
  now reaches "fully drawn" 17 ms *sooner* (95% CI −26 to −8 ms, −3.1%): Home's first load
  syncs and reads SQLite, which kmpCore does in Kotlin off the JS thread. Small, but the first
  measurable KMP advantage on real work.
- **Scrolling is the same in both builds (BM-02, the control).** Flinging through 1,000 History
  entries, in two sessions: frame rate, CPU per thread, peak RAM and now janky frames (0.8% vs
  0.9%) all within the noise, none meaningful. The setup is fair, so differences found in other
  scenarios can be trusted.
- **In a real user flow, the app's call pattern mattered more than where the core runs (BM-07).**
  Sending money (Home → recipient → amount → review → PIN → result) runs at the same ~58 fps in
  both builds. The first session found two library effects: kmpCore ~80–90 ms faster on each step
  that read secure storage (react-native-sensitive-info's extra Keystore round trips), and ~390 ms
  slower on the PIN (javax.crypto vs quick-crypto's OpenSSL). Keeping the user's phone in memory
  and making the amount step's two backend calls in parallel cut the app's step time by **25%
  in jsCore (1.97 → 1.48 s) and 19% in kmpCore (2.20 → 1.79 s)** (`2026-10-17_mid-05`, replicated
  by mid-04), and the secure-storage difference disappeared. What's left is the PIN (+340 ms), a
  crypto library choice, which also makes kmpCore's CPU +4 points and its process ~28 MB larger
  after the unlock.
- **Still open:** streams (BM-05), where KMP should keep the JS thread free.

**Note under H6.** One Perfetto trace per build shows where startup time goes: after the first
frame, the UI thread spends ~170 ms mounting and drawing Home's native views, and the JS thread

Kotlin's own threads use ~2 ms. Where the business logic runs barely matters at startup, so the
cases where KMP could win are BM-03, BM-04 and BM-05.

## Results by scenario

### BM-01: cold start → Home rendered
Session `2026-10-05_mid-02` (slice 4), release builds, 2 warm-up + 20 measured per build,
alternating, all launches cold. Battery 32.2–33.0 °C.

| Metric | jsCore median | kmpCore median | Shift (kmp − js) | 95% CI | p |
|---|---:|---:|---:|---|---:|
| Time to initial display | 256.5 ms | 260.5 ms | +4.0 ms | −3.0 to +11.0 ms | 0.19 |
| Time to fully drawn (Home with data) | 527.5 ms | 511.0 ms | **−17.0 ms** | −26.0 to −8.0 ms | 0.001 |

Shift is the Hodges–Lehmann estimate; the CI is distribution-free and states the largest

**Time to fully drawn.** The shift is real (p = 0.001, IQRs don't overlap) but below the 5%

before Home can draw, it now syncs the server's changes into the replica and reads wallet, recent
transactions and the monthly summary from SQLite. kmpCore does that in Kotlin on its own
threads; jsCore does it in JS on the JS thread (plus op-sqlite's native calls).

Earlier session (`2026-10-04_mid-01`, Home slice, in-memory storage): TTID +1.0 ms (CI −6 to
+9), TTFD +3.0 ms (CI −7 to +14).

**Across sessions** (not a build comparison): time to fully drawn went from ~294 ms
(placeholder) to ~474–481 ms (real Home) to ~511–528 ms (slice 4: replica sync and SQLite reads,
navigation) in **both** builds. Compare builds within a session only.

| Frame time p90 / p99 (`gfxinfo`) | 16.0 / 23.0 ms | 16.5 / 23.0 ms | +0.0 / +0.0 ms | 0.0 to +2.0 / −1.0 to +1.0 ms | 0.28 / 0.67 |
| CPU, whole app (100% = 1 core) | 133.6% | 136.3% | +2.8 pp | −0.7 to +8.6 pp | 0.21 |

No metric passes the §4.3 rule. Two iterations (both jsCore) lost frame-trace events; they
completed, so they are kept (§4.3), and gfxinfo, which counts frames separately, has all 20.
Janky frames is a rate under 5%, judged in points (§4.3). RenderThread CPU has CV 11.7% in
kmpCore (three high iterations late in the session), over the 10% rule; kept with a note in the
session's NOTES.md.

**Across sessions.** Frame rates were 44.5 / 44.6 fps on `2026-10-05_mid-01` and 42.5 / 42.5
fps here; the phone's OS was updated in between and temperatures differ. Compare builds within
a session, not frame rates across sessions. The earlier session also found no meaningful
difference (frame rate +0.1%, app CPU −3.7%, RenderThread CV 17–20% in both builds).

**Reading the frame rate.** The ROM ran Pocketly at 60 Hz, and the ~1,550 half-second samples
per build have the same distribution (p10 36.1 vs 36.2, p50 40.1 vs 40.0, p90 53.9 vs 53.8
fps; a few dips to 10–15 fps in both). The average is below 60 because each injected fling is a separate `adb` call:
the list coasts to rest between flings, and Android draws nothing when nothing moves. So it
reflects the gesture rhythm, not jank, and it is identical in both builds, which is what a
control should show.

**Why the control holds.** Scrolling reads the local replica 20 rows at a time and renders
them; the work is FlashList layout and native drawing, which is the same code in both builds.
The core is only called once per page.

### BM-03: spending summary over 10,000 entries
Session `2026-10-11_mid-01`, `perf` builds, in-app harness: 5 cold starts per build
(alternating), each 5 warm-up + 10 measured runs → 50 per build. Battery 29.2–31.8 °C. Both
builds read the same 10,000 entries and produced the same summary (checksums in `summary.md`).

| Per run (median) | jsCore | kmpCore | Shift (kmp − js) | 95% CI |
|---|---:|---:|---:|---|
| **End-to-end** (`computeSpendingSummary`, timed in JS) | 52.8 ms | 42.3 ms | **−10.5 ms (−20%)** | −14.8 to −9.6 ms |
| Compute (the summary itself) | 4.7 ms | 0.4 ms | −4.3 ms (−92%) | −4.4 to −4.3 ms |
| Storage (reading the replica) | 47.7 ms | 41.2 ms | −6.6 ms (−14%) | −11.3 to −5.8 ms |
| Bridge overhead (end-to-end − compute − storage) | 0.0 ms | 0.6 ms | +0.6 ms | |

**Reading it.** The calculation is ten times faster in Kotlin, but it's a few milliseconds
either way. Most of the time is **reading 10,000 rows from SQLite**, and there the builds use
different libraries (op-sqlite in jsCore, SQLDelight on the platform SQLite in kmpCore;
ADR-0009), so the storage gain is partly the library and partly turning rows into objects
(Hermes objects vs Kotlin objects). jsCore's reads slow down within each launch (~50 ms on the
first runs, 58–68 ms by the tenth; storage CV 10.6%), consistent with garbage collection while
it materializes the rows; kmpCore stays at 41–45 ms. BM-03 ran three times this session: the
first attempt stopped on lost logs and the second was set aside because one kmpCore cold start
ran ~6.7× slower throughout (CV 110%); both are kept in the results folder.

Earlier session (`2026-10-05_mid-03`): 59.1 vs 41.3 ms end-to-end (−30%), compute 4.6 vs 0.4 ms.

### BM-04: ingest 5,000 transactions
Same session and protocol. The payload is 1.3 MB of JSON, identical in both builds; before
every run the replica is reset to the same 200 entries (not timed). Both builds accepted all
5,000 in every run (checksums).

| Per run (median) | jsCore | kmpCore | Shift (kmp − js) | 95% CI |
|---|---:|---:|---:|---|
| **End-to-end** (`ingestTransactions`, timed in JS) | 64.9 ms | 71.4 ms | **+9.2 ms (+10%)** | +6.1 to +13.8 ms |
| Parse + validate (compute) | 27.3 ms | 20.0 ms | −3.0 ms (−27%, not meaningful) | −5.2 to +0.4 ms |
| Write to the replica (storage) | 39.3 ms | 40.1 ms | +1.0 ms (+2%, not meaningful) | −0.0 to +2.2 ms |
| Bridge overhead (1.3 MB string in, result out) | 0.0 ms | 9.8 ms | +9.7 ms | +9.6 to +10.2 ms |

**What changed since the last session.** Until `a9cf596`, jsCore wrote the rows with op-sqlite's
`executeBatch`, which ran in one transaction but prepared the INSERT again for every row;
kmpCore's SQLDelight reuses one prepared statement. jsCore now does the same, and its write time
fell from 76.7 to 39.3 ms, level with kmpCore. **The earlier "writes twice as fast in kmpCore" was
jsCore's code, not the SQLite library: the fair comparison only appeared once both cores used the
same write strategy.** With that difference gone, kmpCore's lead (−38% on `2026-10-05_mid-03`)
turns into a 10% deficit: its parsing is faster, but passing the 1.3 MB string through Nitro
costs 9.8 ms.

**kmpCore's parsing is uneven: median 20.0 ms, p90 38.0 ms** (jsCore 27.3 / 30.2 ms). In 4 of 5
launches, parse + validate runs at ~19 ms for the first five measured runs, then steps up to
30–50 ms and stays there (CV 35.7%); the fifth launch stays at 15–22 ms. That spread is why the
compute difference isn't meaningful by the §4.3 rule. Garbage collection in ART is the first
suspect (kmpCore's Java heap PSS also swings between ~8 and ~26 MB across the memory rounds); one
system trace of a launch would confirm it. Not rerun.

#### BM-04b: the payload already in the core
Session `2026-10-11_mid-02`, same protocol, run right after a BM-04 rerun. BM-04 passes the
1.3 MB payload from JS inside the timed call; in a KMP app whose core owns the network, the
response would arrive in Kotlin and never cross the bridge. BM-04b stages the same payload in
the core before each run (`stageIngestPayload`, not timed) and times `ingestStaged()`.

| Per run (median, n = 50) | BM-04 jsCore | BM-04 kmpCore | BM-04b jsCore | BM-04b kmpCore |
|---|---:|---:|---:|---:|
| **End-to-end** | 65.2 ms | 81.3 ms | 66.1 ms | 72.9 ms |
| Parse + validate | 26.4 ms | 24.7 ms | 27.4 ms | 31.1 ms |
| Write | 38.5 ms | 40.6 ms | 38.7 ms | 40.1 ms |
| Bridge overhead | 0.0 ms | 9.9 ms | 0.0 ms | 0.7 ms |
| kmpCore − jsCore, end-to-end | | **+14.3 ms (+25%)**, CI +8.1 to +19.4 | | **+5.6 ms (+10%), not meaningful**, CI +0.9 to +8.3 |

**Reading it.** Owning the network removes the bridge cost (9.9 → 0.7 ms), and jsCore is
unchanged, as it should be. What's left is the parse step, and it isn't stable in kmpCore: in
every launch it takes 17–21 ms for about the first ten imports since the process started, then
30–64 ms for the rest. Before the step, kmpCore's BM-04b runs take ~60 ms end-to-end (faster than
jsCore's ~66 ms); after it, ~76 ms. So "the core owns the network" makes KMP competitive for
imports, not clearly better, until the slowdown is understood. The same step showed up in 4 of 5
BM-04 launches on `2026-10-11_mid-01`.

#### BM-04 memory
Separate memory rounds (5 cold starts per build; benchmarking.md §5.2): resident memory sampled
every ~3.4 ms on the device, lined up with the harness's phase markers. Session
`2026-10-11_mid-02` (the same numbers as `mid-01` within 1 MB).

| Per cold start (median) | jsCore | kmpCore | Shift (kmp − js) | 95% CI |
|---|---:|---:|---:|---|
| RSS at launch (first second sampled, before setup) | 171.1 MB | 175.7 MB | +4.5 MB (+2.7%, not meaningful) | +2.2 to +5.5 MB |
| **RSS after setup and 5 warm-up imports** | 200.5 MB | 262.3 MB | **+61.8 MB (+31%)** | +61.6 to +62.1 MB |
| PSS after the run (`dumpsys meminfo`) | 106.8 MB | 167.8 MB | +61.0 MB | +59.9 to +63.0 MB |
| Peak RSS over the measured runs, minus the line above | 3.6 MB | 2.0 MB | −1.6 MB | −2.1 to −0.3 MB |

**Where the gap comes from** (`2026-10-11_mid-02` NOTES.md):
- At a normal cold start to Home, without benchmark mode, both builds use PSS ~116 MB and RSS
  ~238 MB.
- During BM-04's setup and warm-up, jsCore grows ~40 MB and kmpCore ~101 MB.
- A minute after a BM-04 run, jsCore is back at its launch size (PSS 116 MB) while kmpCore holds
  PSS 225 MB. The extra ~110 MB is **private clean pages in the ART heap**; live Java objects are
  5.0 MB in both builds. Which mapping holds them can't be read from `adb shell` on a release
  build; a heap profile would show it.

**Reading it.** KMP doesn't make the process bigger at rest. Parsing large payloads in Kotlin
leaves memory behind that ART doesn't return quickly, which matters on low-end phones (not
measured yet) and is probably linked to the parse slowdown above. The ingest itself adds only a
few MB at its peak in either build; kmpCore's figure is within the ~2 MB of swapped-in zygote
pages it gets in every round.

### BM-06: bridge calls (10,000 amounts)
Same session and protocol. Both builds formatted the same 10,000 amounts to the same strings.

| Per run (median) | jsCore | kmpCore | Shift (kmp − js) |
|---|---:|---:|---:|
| **10,000 × `formatMoney`** (chatty) | 13.3 ms | 10.6 ms | **−2.7 ms (−20%)** |
| **1 × `formatMoneyBatch(10,000)`**, end-to-end | 11.0 ms | 5.6 ms | **−5.2 ms (−49%)** |
| · formatting (compute) | 11.0 ms | 2.2 ms | −8.7 ms |
| · bridge (10,000 numbers in, 10,000 strings out) | 0.0 ms | 3.3 ms | +3.3 ms |
| **10,000 × `echo`** (a call that does nothing) | 1.2 ms | 4.2 ms | **+3.0 ms** |

**Reading it.** `echo` isolates the cost of a call: ~0.12 µs as a plain JS call, ~0.42 µs through
Nitro into Kotlin, so trivial calls are ~3.5× slower in kmpCore, ~0.3 µs of bridge each.
Formatting a number costs ~1.1 µs in JS (batch: 11.0 ms / 10,000) and ~0.22 µs in Kotlin (2.2 ms
/ 10,000), a saving of ~0.9 µs that covers the crossing, so even the chatty pattern is faster in
kmpCore. **Rule: moving a function to Kotlin pays off when it saves more than ~0.3 µs per call.** Batching still halves
the time: 3.3 ms to move 10,000 values each way is far less than 10,000 separate calls. For
bridge API design (ADR-worthy), batch when you have the data in hand, but don't contort an API
to avoid single calls.

Earlier session (`2026-10-05_mid-03`): chatty 13.0 vs 10.5 ms, batch 10.8 vs 5.5 ms.

### BM-07: full transfer flow
Session `2026-10-17_mid-03` (slice 6), perf builds from `90ba6b6`, 5 alternating blocks × 2 per
build after a warm-up, n = 10 per build, none excluded. Fake latency 300 ms; PIN confirmation
(biometrics off). Flashlight over an adb-input driver; the step times are the app's own
`performance.now()` marks (benchmarking.md, BM-07 note). Battery 35.3–36.5 °C. Checklist met
except the screen timeout (10 min, no effect).

| Step (median) | jsCore | kmpCore | kmpCore − jsCore |
|---|---:|---:|---|
| Send → recipients on screen (1 backend call + secure-storage read) | 521.5 ms | 440.8 ms | −78 ms (CI −95 to −70) |
| Contact → amount screen (2 backend calls + secure-storage read) | 785.1 ms | 694.9 ms | −91 ms (CI −98 to −88) |
| Review → review screen | 23.9 ms | 20.6 ms | −3.5 ms |
| Confirm → PIN screen | 20.8 ms | 29.6 ms | not meaningful |
| PIN → result (PBKDF2 × 600,000 + 300 ms submit) | 622.1 ms | 997.1 ms | +387 ms (CI +365 to +414) |
| **Sum of steps** | **1,966.9 ms** | **2,198.3 ms** | **+216 ms (+11.8%)** |
| UI frame rate | 58.4 fps | 58.4 fps | none |
| CPU all threads / JS thread | 26.0% / 4.6% | 29.8% / 4.2% | +3.8 / −0.4 points |

**What it means.** Screen transitions run the same in both builds: frame rate and UI/Render
thread CPU match, so H4 holds beyond scrolling. The totals are decided by two library choices,
not by where the logic runs. The PIN step is +387 ms in kmpCore, within 10% of BM-11's
quick-check gap for the same hash (quick-crypto's OpenSSL 201 ms vs javax.crypto 554 ms); that
extra hashing is also most of kmpCore's +3.8 points of CPU. The two steps that start a transfer
read this install's phone from secure storage, and there kmpCore is ~80–90 ms faster, about what
react-native-sensitive-info's extra Keystore round trips cost per read in BM-01-lock's trace
(~78 ms); a fit, not traced in this session. Reading it once per flow would remove most of it in
jsCore (ADR-0002: fewer, coarser calls). For a user, the difference is a PIN that feels ~0.4 s
slower in kmpCore; with biometrics (the default once enabled), neither build hashes a PIN.

The extra CPU is kmpCore's own coroutine pool (`DefaultDispatch`, +4.5 points), mostly the PIN
hash, which costs ~600 ms of JVM work per flow where quick-crypto spends ~50 ms of CPU (its
201 ms in BM-11 is mostly waiting on secure storage); GC adds +0.3 points. Per-thread totals
account for all of Flashlight's +4.1 points.

**Measured, then fixed** (session `2026-10-17_mid-05`, same method, unlocking on the lock screen
before each flow, ADR-0014 §6; `2026-10-17_mid-04` replicates it). The two steps that read
secure storage now read the phone from memory, and the amount step's backend calls run in
parallel:

The library difference on secure storage is gone; the PIN remains (+340 ms, the javax.crypto vs
quick-crypto gap of BM-11). The extra CPU is all kmpCore's coroutine pool (the PIN hash, +3.9)
and GC (+0.4), less quick-crypto's thread (−0.4); JS, UI and Render threads are the same in both
builds. Unlocking first (mid-03 skipped the lock screen) shows kmpCore's process ~28 MB larger
during the flow: the PIN check's JVM work grows the ART heap and it stays, as in BM-04's memory
rounds.

**Replication.** mid-04, the first run after the fixes, gives the same picture: sum of steps
1.46 vs 1.79 s, PIN +344 ms, peak RSS +25.9 MB, recipients −5 ms. Its CPU rows had a CV over 10%
from one kmpCore iteration disturbed by something outside the app, so §4.3 asked for a rerun:
mid-05, same code and method, has no CV warning on any metric. The amount step is the one thing
the two disagree on (kmpCore −13 ms in mid-04, not meaningful; −33 ms in mid-05, meaningful by
the rule): not a finding until a third session or a trace settles it.

**How the step times are taken.** Each "-shown" mark is the screen's first JS effect after its
data arrived: after React commits, before the frame reaches the screen, like BM-01's original
marker. Both builds are measured at the same point, so the comparison is fair, but the absolute
times understate what a user sees by roughly a frame or three (~20–50 ms at 60 Hz).

### BM-08: app size (arm64-v8a)

Every ABI's APK is smaller in kmpCore (−405 to −805 KB). **That total mixes two effects**, which

**What this means.** The comparison is realistic: most React Native apps that need SQLite ship a
bundled one, as op-sqlite does. But the size win comes from that storage choice, not from KMP.
An app that already bundles SQLite would see roughly the architecture's cost, about +250 KB of
download; one that could use the platform's SQLite from JavaScript too would lose the win.

## Bridge overhead
Overhead = end-to-end (timed in JS) − compute − storage (timed inside the core). For jsCore it is
~0 by construction, so only kmpCore's matters:

| What crosses the bridge | kmpCore overhead (median) | Share of kmpCore end-to-end |
|---|---:|---:|
| BM-03: month string in, `SpendingSummary` out | 0.6 ms | 1% |
| BM-04: 1.3 MB JSON string in, `IngestResult` out | 9.8 ms | 14% |
| BM-04b: nothing in (payload already staged), `IngestResult` out | 0.7 ms | 1% |
| BM-06: 10,000 numbers in, 10,000 strings out (one call) | 3.3 ms | 59% |
| BM-06: one call that does nothing (`echo`), vs the same call in JS | ~0.3 µs | — |

Session `2026-10-11_mid-01`. The overhead grows with the size of what crosses, not with the
work behind it. Large strings and arrays are the cost to watch: in BM-04 the 9.8 ms for the
JSON input is what turns kmpCore's faster parsing into a slower import. Individual calls are
not.

## Limitations
- One mid-range device; no low-end device yet. Android only.
- In-process fake backend, persisted in SQLite like the replica (ADR-0009). Numbers measured before slice 4 used in-memory storage and are not comparable with later runs.
- BM-01 uses platform startup logs instead of Macrobenchmark, which is unreliable on this ROM
  (benchmarking.md §5); page cache isn't dropped between runs (no root), the same for both builds.
- `libNitroModules.so` (958 KB APK) ships in **both** builds (ADR-0003), so the deltas above
  understate the total cost of adopting Nitro + KMP from a bare app.
- Trace findings come from one cold start per build: indicative, not statistics.
- BM-02 drives the flings with `adb shell input` rather than Maestro, whose driver hangs on this
  ROM (benchmarking.md §5). Fling cadence is set by `adb` (~0.25 s per fling), the same for both
  builds. Flashlight's frame-time tracer dropped events in 2 of the 20 iterations (234 and
  14,738 lost events); their frame rates sit inside the rest of the distribution, so they stay in.
- BM-02 ran over USB with the phone on its charger; a first attempt over wireless `adb` lost its
  connection, and an earlier attempt without a temperature gate drifted from 39 °C to 45 °C and
  was discarded.

- BM-03/04/06 time end-to-end in JS with `performance.now()` and compute/storage inside each
  core; the two cores' storage timers wrap different libraries (§3.3), though since
  `2026-10-11_mid-01` both write in bulk the same way (one transaction, one prepared statement).
  CV exceeds 10% for some rows of that session (jsCore BM-03 storage 10.6%, BM-04 compute 12–36%,
  BM-04 and BM-06 kmpCore bridge overhead 12–16%): patterns inside each launch, repeated in
  every round, reported as measured and listed in the session's NOTES.md.
- On the vivo, some cold starts run without any of their log lines reaching logcat. The harness
  runner relaunches them (7 of 47 launches in the kept results of `2026-10-11_mid-01`, 11 of 64 over the whole session, both builds) and counts them
  as failed iterations (§4.3).
- BM-04 memory is resident memory (RSS) sampled every ~3.4 ms; a peak shorter than that can be
  missed. The phone swaps to zram, so kmpCore's small ingest figures (~2 MB) are within the
  swap-in noise; the ~60 MB retained after the warm-up imports is not. That retained memory is
  measured after a benchmark workload (repeated 1.3 MB imports), not at rest.
- The phone's OS was updated between `2026-10-05` and `2026-10-11` (16.0.19.3 → 16.0.21.0).

## Found by benchmarking
BM-02 crashed `jsCore` mid-scroll on its first attempt: *"Unable to find parentView for tag"*,
preceded by dozens of *"Unable to find viewState for tag"* warnings per run, on the phone and
(fewer) on an emulator. Cause: React Native 0.87 keeps its native view registry in an
`androidx.collection` map that versions 1.4.0–1.4.2 can corrupt
([reactwg/react-native-releases#1426](https://github.com/reactwg/react-native-releases/issues/1426)),
and the app resolved 1.4.2. Fast list recycling loses views until a missing parent crashes the
app. Forcing `androidx.collection` 1.4.4 (`apps/mobile/android/app/build.gradle`, until RN 0.88)
took the warnings from 24–73 per run to 0 in both builds. Both builds had the bug; it would
have hit users of either.

## Not part of the comparison
The ~170 ms of UI-thread work after the first frame (mounting SVG icons, the gradient, the
list) is paid equally by both builds. Lighter icons or fewer views would make **both** faster,
which is a UX improvement, not a KMP finding. Deferred.

## When I'd choose each
_Interim, before BM-05._ Neither startup, scrolling, a full user flow (BM-07) nor download size is
a reason to avoid KMP: they're the same, or differ by a fixed ~250 KB; in the transfer flow the
differences came from the crypto and secure-storage libraries each build uses, which are choices
in either architecture. **KMP pays off when the work happens
where the data already is, and only results cross the bridge**: a summary over 10,000 records
ran 20% faster end-to-end. It doesn't when megabytes must cross the bridge to reach Kotlin
(importing 5,000 records from JS: 10–25% slower). Owning the network in Kotlin removes that cost
but, today, doesn't make imports faster: Kotlin's parsing slows down after repeated large
payloads and the memory they leave behind stays (~110 MB a minute later). Fetch and parse large
payloads where they will be used, keep bridge traffic to results, and move a function to Kotlin
only if it saves more than ~0.3 µs per call. If an app's core is thin (format, validate, forward
to a server), the gain is a few milliseconds and doesn't justify a second language.
