# ADR-0002: Nitro Modules for the JS ⇄ Kotlin bridge

**Status:** Accepted · 2026-10-03 · Resolves the "Bridge" question in [product.md](../product.md) §9 / §11

## Context

The bridge choice directly shapes hypothesis H3 (many tiny calls are slower in `kmpCore`).
The options were:

| Option | Notes |
|---|---|
| Hand-written Turbo Modules | The RN default. Codegen from TS specs, JSI underneath, Java/ObjC++ glue |
| reakt-native-toolkit | Generates RN modules from Kotlin annotations. Product.md flagged doubts about RN-version compatibility |
| **Nitro Modules** | JSI HybridObjects with typed C++ ⇄ Kotlin/Swift bindings generated by `nitrogen`. Lowest per-call overhead of the three |

## Decision

Use **Nitro Modules 0.37** (`react-native-nitro-modules` + `nitrogen`).

- The spec is `packages/core-kmp/src/specs/PocketlyCore.nitro.ts`. It **imports its struct and
  enum types from `@pocketly/core-contract`** instead of redeclaring them, so NFR-ARCH-05 holds:
  every bridged type is declared once.
- `HybridPocketlyCore` (Kotlin and Swift) is a thin adapter. It turns JS doubles into exact
  `Long`s (`BridgeConversions`) and maps domain types to Nitro structs. All logic stays in
  `shared/.../bridge/PocketlyCore`.
- Async methods return Nitro `Promise`s backed by coroutines (Android) or Swift `async` (iOS).
  Streams use a Nitro callback plus a `PriceSubscription` HybridObject; inside Kotlin they are
  `Flow`s (NFR-ARCH-04).

## Consequences

- H3 is measured against the *fastest* mainstream bridge. If chatty calls still lose, that's a
  strong result. If they don't, the report has to say the result might not hold with Turbo Modules.
- `nitrogen` output (`packages/core-kmp/nitrogen/generated`) is committed and must be
  regenerated (`yarn nitrogen`) whenever the spec or a contract type changes.
- Nitro is less common than Turbo Modules, so the README documents setup in detail.
